# Atualização do aplicativo

Versão local atual: `0.4.0` (`app/core/version.py`, também publicada como `FastAPI.version`). O versionamento desta entrega segue a convenção `major.release.minor`; a tag correspondente planejada é `DEV-v0.4.0`.

## DEV a partir do checkout

A tela `/updates` oferece **Verificar versão do checkout**. O endpoint lê `APP_VERSION` dos arquivos já presentes no checkout, sem importar ou executar o arquivo. Quando a versão em disco for superior à carregada, **Reiniciar e aplicar versão do projeto** solicita o fechamento da janela; o launcher encerra o servidor e executa o hook normal de shutdown/saves, libera o mutex e inicia novamente `sys.executable -m app.desktop` a partir da raiz deste checkout. Assim o processo recarrega os arquivos Python, templates, CSS e JavaScript já existentes no disco. Essa ação não busca código, não executa `git pull`, não baixa nem substitui arquivos. O checkout tem `origin` apontando para o repositório público, mas o botão não faz pull. O botão não aparece no modo frozen.

## Atualizar uma cópia instalada

Pacotes `sys.frozen` podem consultar o GitHub Releases quando a chave pública Ed25519 de distribuição está embutida. Owner/repo têm fallback `Vitor41/guild_idle_manager`; o canal vem do marcador da instalação. A consulta só ocorre ao pressionar o botão; o módulo valida a release/tag e semântica prerelease do canal, a assinatura dos bytes do manifesto, o produto/schema/SemVer/mínimo e o SHA-256 do Setup antes de habilitar a instalação. O Setup é baixado para uma pasta temporária dedicada, revalidado pelo hash ao solicitar a instalação e só é aberto após confirmação explícita; o launcher fecha o app e aguarda seu processo terminar antes de abrir o instalador. O bootstrap 0.3.3 incluirá a chave pública Ed25519; a atualização remota só será habilitada após publicar uma release DEV assinada válida.

O instalador recebe o canal (`DEV`, `beta` ou `stable`) do pacote, exige que um destino existente tenha o mesmo marcador de produto/canal, executa seu smoke offline na cópia staged e troca os arquivos com backup/rollback. Os saves permanecem em `%LOCALAPPDATA%\GuildIdleManager\saves`. O build pode selecionar o canal com `scripts/build_desktop_dev.ps1 -Channel stable` ou `-Channel beta`; o default preserva DEV. O Setup DEV 0.3.1 foi construído e validado sem ser executado ou instalado; o caminho e as verificações estão no relatório de aceite.

## Situação

**Canal e confiança.** Owner/repo padrão são `Vitor41/guild_idle_manager`. Em execução empacotada, owner, repo e chave pública vêm de `app/data/gim-release-config.json`; o canal é lido do marcador da instalação (`DEV`, `beta` ou `stable`). No checkout, owner/repo podem ser configurados por ambiente e o canal padrão é `DEV`. O cliente continua fechado enquanto não houver uma chave pública Ed25519 válida embutida. O marcador e owner/repo não substituem assinatura nem hash.

A instalação 0.3.1 atualmente distribuída não tem chave pública embutida e, por isso, mantém consulta/instalação remota desativada. Ela não pode confiar retroativamente em uma chave baixada da internet: a primeira versão com a chave pública precisa ser instalada manualmente. O repositório `Vitor41/guild_idle_manager` agora está público, mas a API pública de Releases ainda não contém releases. O atualizador usa acesso anônimo e não contém token.

Para habilitar distribuição, gere uma chave Ed25519 fora do repositório com `scripts/generate_release_key.py`. Cadastre o Base64 privado como segredo `GIM_RELEASE_PRIVATE_KEY_B64` e o Base64 público como variável `GIM_RELEASE_PUBLIC_KEY_B64` nas configurações Actions do repositório. O workflow `.github/workflows/publish-dev-release.yml` usa esses valores para empacotar o Setup com a chave pública, assinar o manifesto com a chave privada e publicar uma release DEV. A chave privada nunca entra no Git, bundle ou log da ação. A versão 0.3.1 instalada precisa receber o Setup bootstrap 0.3.2 manualmente uma vez.

## Contrato GitHub Releases v1

- Configuração: owner/repo padrão `Vitor41/guild_idle_manager`; o build aceita `-GitHubOwner` e `-GitHubRepo` e os salva, junto com `public_key_b64`, em `app/data/gim-release-config.json` (schema 1). Owner tem slug alfanumérico/hífens de até 39 caracteres; repo aceita alfanumérico, ponto, sublinhado e hífen até 100 caracteres, sem `..` ou sufixo `.git`. Config ausente em bundles 0.3.1 legados mantém defaults e lê a antiga chave pública opcional `gim-release-public-key.txt`; config presente mas inválido falha fechado. `GIM_GITHUB_RELEASES_OWNER`, `GIM_GITHUB_RELEASES_REPO`, `GIM_GITHUB_RELEASES_CHANNEL` e `GIM_GITHUB_RELEASES_PUBLIC_KEY` são overrides apenas para DEV frozen e para o checkout. `GIM_GITHUB_RELEASES_MANIFEST_ASSET` seleciona o asset JSON em DEV; por padrão `gim-release.json`.
- Canal `stable` usa releases estáveis; `beta` e `DEV` usam releases prerelease. A tag segue `<channel>-v<version>` (por exemplo, `stable-v1.2.3`, `beta-v1.2.3` ou `DEV-v1.2.3`). No pacote frozen, o canal é determinado pelo marcador instalado; no checkout, `DEV` é o padrão. A chave pública não tem valor padrão: sem a chave válida embutida, o cliente não consulta o GitHub e mantém o updater fechado. Manifesto com nome inválido também bloqueia a configuração.
- Cada release contém o asset JSON do manifesto e o asset de assinatura destacado `<manifesto>.sig`. A assinatura Base64 Ed25519 cobre os bytes exatos do manifesto. O manifesto UTF-8 contém `schema_version` (inteiro `1`), `app_id` (`guild-idle-manager`), `version` (SemVer), `channel`, `minimum_supported_version`, `asset_name` (nome do instalador anexado à mesma release) e `asset_sha256` (64 caracteres hexadecimais minúsculos). Releases devem marcar prerelease de acordo com o canal.
- O cliente confere canal/tag, prerelease, schema, app id, SemVer, versão mínima, presença do asset, assinatura pela chave embutida e SHA-256 antes de oferecer um Setup. Falhas bloqueiam download ou instalação. `minimum_supported_version` marca atualizações obrigatórias na mensagem; toda atualização ainda exige confirmação explícita. `/updates/check` pode baixar apenas para staging temporário; `/updates/install-release` exige o estado verificado mantido no processo e recalcula o SHA-256 antes do handoff ao Setup.
- O Setup aplica os arquivos do app através de staging, smoke offline, backup temporário e rollback em falha; os saves ficam fora da árvore instalada. O handoff espera o encerramento do app antes de iniciar Setup. A configuração sem chave mantém o fluxo fail-closed. O build DEV 0.3.1 foi validado estruturalmente, mas não foi executado, instalado, nem inspecionado em GUI. Os testes e evidências do Setup estão em `docs/HOTFIX_0_3_1_ACCEPTANCE.md`.

## Requisitos para distribuição

Antes de distribuição, confirmar acesso anônimo ao repositório, gerar e proteger a chave privada fora do Git, empacotar a chave pública, publicar Setup/manifesto/assinatura consistentes e conferir o pacote publicado. O produto não migra nem copia saves porque o Setup substitui somente a árvore de programa; qualquer migração futura precisa de backup próprio.

## Bootstrap DEV 0.3.3

O checkout prepara o bootstrap 0.3.3. Instalações anteriores sem chave pública embutida não podem aceitar confiança retroativamente e precisam receber o novo Setup manualmente uma vez. A chave privada deve ficar fora do repositório e ser armazenada como segredo do ambiente Actions `release-signing` (`GIM_RELEASE_PRIVATE_KEY_B64`); nunca deve ser commitada. Cadastre a chave pública correspondente como variável do repositório (`GIM_RELEASE_PUBLIC_KEY_B64`).

O workflow `.github/workflows/publish-dev-release.yml` só roda manualmente a partir do branch principal e valida que a tag `DEV-vX.Y.Z` aponta para um commit já integrado nele, além de exigir que `app/core/version.py` corresponda à tag. Antes de rodar, crie o ambiente Actions `release-signing`, configure o segredo privado e a variável pública. O build embute a chave pública; o signer confirma que a privada corresponde à pública antes de assinar; o workflow publica Setup, manifesto e assinatura como prerelease. A release 0.3.3 só poderá ser publicada depois que esse commit estiver integrado ao branch padrão e o ambiente Actions estiver configurado. Use a tag `DEV-v0.3.3` para publicar esta versão.
