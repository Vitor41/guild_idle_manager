## Concorrência dos gatilhos de eventos

O achado de concorrência está tratado para o runtime desktop distribuído. `create_cycle_portals` e `evaluate_open_rebellion` adquirem um lock por campanha mantido até o fim da transação SQLAlchemy, para que a próxima thread veja o evento já commitado e retorne idempotentemente. A regressão concorrente usa duas sessões e cobre simultaneamente a criação de portal por região/ciclo e a escolha única da rebelião global; não houve exceção de serviço/request. O índice único existente em `RegionalEvent` cobre ainda uma repetição do mesmo tipo/ciclo/região.

O launcher não tinha garantia de instância única. Agora usa mutex Windows nomeado com identidade derivada de `%LOCALAPPDATA%`; uma segunda instância com o mesmo perfil de dados é recusada antes de abrir o servidor local. Isso fecha o limite cross-process para a distribuição desktop, que executa um único launcher por perfil. Testes unitários isolados cobrem primeira aquisição, `ERROR_ALREADY_EXISTS`, erro Win32 residual zerado antes da criação, retorno limpo da segunda inicialização e liberação/fechamento no cleanup (`tests.test_desktop_launcher`). Isso não substitui um smoke nativo do launcher na build final, que continua pendente. A trava Python permanece process-local e não foi apresentada como proteção para escritores externos ao launcher.

O mapa conserva um lock pequeno por cada campanha vista até o processo terminar. Não os removemos após liberar: uma thread pode estar aguardando o lock antigo, e removê-lo sem contagem/coordenação pode permitir que outra thread crie um segundo lock para a mesma campanha. A vida útil curta do launcher limita esse custo; cada entrada é um objeto de lock.
